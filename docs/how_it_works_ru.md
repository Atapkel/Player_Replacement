# Как работает Replacement Finder: подробно и простыми словами

Это объяснение всего проекта от начала до конца: от сырого файла с данными до короткого списка игроков на экране и
проверки, которая доказывает, что система работает. Код читать заранее не нужно. Там, где это полезно, указано, какой
файл и какая функция делают каждый шаг, чтобы потом можно было открыть код и узнать то, о чем здесь говорится.

Через весь текст мы проведем **один реальный пример**: летом 2022 года «Брайтон» продает своего опорного полузащитника
Иву Биссуму в «Тоттенхэм» и хочет найти замену максимум за 25 миллионов евро.

---

## Общая картина в одном абзаце

Мы берем рейтинги игроков FIFA за десять лет. Для игрока, которого клуб продает, сначала собираем всех, кто может играть
на его позиции и укладывается в денежные ограничения клуба. Из них оставляем тех, чей **стиль игры** ближе всего к
проданному игроку. Это обучение без учителя: никто не объясняет компьютеру, что такое «похожий стиль», он сам измеряет
сходство по навыкам. Затем мы **предсказываем, насколько хорош будет каждый из них через два года**, с помощью модели,
обученной на прошлых сезонах. Это обучение с учителем: модель учится на десятках тысяч примеров, где ответ уже известен.
Мы сортируем кандидатов по этому прогнозу и показываем лучших, с объяснениями и предупреждениями. И наконец, чтобы
понять, можно ли всему этому доверять, мы **переигрываем 750 трансферных решений из прошлого** и смотрим, что на самом
деле случилось с игроками, которых купила бы система.

Вот путь нашего примера в цифрах. Запомните эту «воронку»: каждый раздел ниже объясняет один ее шаг.

```
23 803 игрока в FIFA 22
   → 3 055 могут играть на позиции Биссумы (не из «Брайтона», с указанной стоимостью)
   →   535 подходят по бюджету, зарплате, возрасту и минимальному уровню
   →   268 играют в самом похожем стиле (лучшая половина)
   →     5 с лучшим прогнозом рейтинга через два года — это и есть короткий список
```

## Часть 1 · Данные

### A. С чего мы начинаем

Данные — это датасет *FIFA 23 Complete Player Dataset* с Kaggle. EA Sports, компания, которая делает видеоигры FIFA,
дает каждому лицензированному профессиональному игроку числа от 0 до 100: **общий рейтинг** (overall — насколько он
хорош сейчас), **потенциал** (potential — насколько хорошим, по мнению EA, он может стать), шесть общих характеристик
(скорость, удар, пас, дриблинг, защита, физика) и около 35 **подробных навыков**, например короткий пас, перехваты или
отбор в стойке. Также в данных есть возраст игрока, клуб, лига, позиция, рыночная стоимость, недельная зарплата и год
окончания контракта.

Файл охватывает FIFA 15–23, то есть примерно сезоны с 2014/15 по 2022/23. Он огромный — 5,6 ГБ и десять миллионов
строк — по простой причине: EA обновляет рейтинги почти каждую неделю, и файл хранит каждое обновление. Один и тот же
игрок встречается в нем примерно шестьдесят раз за сезон.

### B. Делаем данные удобными (`src/prepare_data.py`)

Шестьдесят еженедельных версий одного игрока нам не нужны, поэтому скрипт очистки оставляет **два снимка на игрока за
сезон**: **начало** сезона (первое обновление, примерно в сентябре, когда выходит игра) и **конец** сезона (последнее
обновление, близко к летнему трансферному окну).

Файл слишком большой, чтобы загрузить его в память целиком, поэтому скрипт читает его **кусками** по 500 000 строк. В
каждом куске он оставляет самое раннее и самое позднее обновление каждого игрока, а в конце повторяет это еще раз для
всех кусков вместе, потому что обновления одного игрока могут оказаться в двух соседних кусках. Еще он читает только
нужные столбцы (например, без ссылок на фотографии) и хранит рейтинги компактными 32-битными числами. Благодаря этому
вся работа занимает около двух с половиной минут и требует не больше 2 ГБ памяти.

По ходу дела скрипт добавляет несколько своих столбцов:

- `season_start` — год, когда начинается реальный сезон. FIFA 22 — это сезон 2021/22, значит 2021.
- `main_position` — первая позиция в списке игрока. У Биссумы указано «CDM, CM», значит его основная позиция CDM (опорный полузащитник).
- `contract_years_left` — сколько лет осталось до конца контракта.

Результат сохраняется в `data/processed/players.parquet`: 393 866 строк, 29 МБ. Parquet — компактный формат файлов,
который pandas читает за секунду.

### C. Готовим данные для модели (`load_players` в `src/finder.py`)

Каждый инструмент проекта начинается с вызова `load_players()`. Эта функция делает три вещи.

Во-первых, оставляет только снимок **конца сезона**, потому что именно его знает клуб, когда открывается летнее
трансферное окно. Остается 196 933 строки: по одной на игрока за сезон.

Во-вторых, превращает 15 позиций FIFA в **8 ролей**: вратарь, центральный защитник, крайний защитник, опорный
полузащитник, центральный полузащитник, атакующий полузащитник, вингер и нападающий. Левый и правый защитник — это одна
и та же работа на разных флангах, поэтому у них общая роль «крайний защитник». А центральный защитник — другая работа,
хотя оба защитники.

В-третьих, считает **силу лиги**: средний рейтинг всех игроков этой лиги в этом сезоне. Это грубая мера (в некоторых
лигах в игре есть только лучшие клубы, как мы увидели в ноутбуке 01), но она дает модели подсказку, к какому уровню
игрок привык.

## Часть 2 · Поиск кандидатов

### D. Набор кандидатов (`ReplacementFinder.candidates`)

Теперь клуб говорит, кого он продает и какие у него ограничения. Кандидат должен пройти все эти правила:

1. **Он может играть эту роль.** Либо у него та же роль, что у проданного игрока, либо он из соседней роли и в его
   списке позиций есть именно позиция проданного игрока. Для Биссумы (опорного полузащитника) это все опорные
   полузащитники плюс центральные полузащитники, которые тоже играют CDM. Центрального защитника, который когда-то играл
   опорного, мы *не* берем: это слишком разная работа. Соседние роли записаны в `NEIGHBOR_ROLES`.
2. **Он не наш игрок.** Своего игрока купить нельзя.
3. **У него есть рыночная стоимость**, и она **в пределах бюджета**: здесь не больше 25 млн евро.
4. **Его зарплата не выше потолка.** По умолчанию это зарплата проданного игрока: 57 тысяч евро в неделю у Биссумы.
5. **Он не старше ограничения по возрасту** (здесь 27 лет, чтобы его еще можно было потом продать).
6. **Он не намного слабее сейчас**: не более чем на 12 пунктов ниже проданного игрока. У Биссумы рейтинг 81, значит у каждого кандидата не меньше 69.

В нашем примере 3 055 игроков могут играть эту роль и не из «Брайтона». После ограничений по деньгам, возрасту и уровню
остается **535**. Эти правила — обычная бизнес-логика, а не машинное обучение, но они важны: модель ранжирует только тех
игроков, которых клуб реально может подписать.

## Часть 3 · Первая составляющая: стиль игры (обучение без учителя)

### E. Превращаем навыки в «профиль стиля»

Два игрока могут оба быть опорными полузащитниками и при этом играть совсем по-разному: один отбирает мяч жесткими
подкатами, другой читает игру и перехватывает передачи, третий в основном раздает пасы. Нам нужна замена, которая
делает **ту же работу**.

У каждого полевого игрока 29 подробных навыков. Если сравнивать эти числа напрямую, сильный и слабый игрок всегда будут
выглядеть разными, просто потому что у сильного все числа выше. Но более дешевая замена почти всегда немного слабее, и
мы не хотим, чтобы это скрывало похожий стиль.

Поэтому мы смотрим на **форму** навыков, а не на их высоту. Для каждого игрока берем его средний навык и вычитаем его из
каждого навыка. То, что остается, показывает, в чем он *относительно* силен и слаб. Это и есть **профиль стиля**.

Средний навык Биссумы — 74,7. Его профиль стиля показывает, что относительно собственного среднего он сильнее всего в
отборе в стойке (+10,3), силе удара и перехватах (по +8,3) и коротком пасе (+7,3), а слабее всего в завершении атак и
пенальти (по −16,7) и закрутке (−12,7). Это описание полузащитника, который отбирает мяч, хорошо пасует и редко забивает
— именно так его описывают люди из футбола.

### F. Как измерить сходство двух стилей: косинусное сходство (`style_similarity`)

Представьте профиль стиля каждого игрока как стрелку в пространстве с 29 направлениями, по одному на каждый навык. У
двух игроков с одинаковым стилем стрелки смотрят в одну сторону. **Косинусное сходство** измеряет угол между двумя
стрелками:

- **1** — ровно одно и то же направление: одинаковый стиль;
- **0** — стили никак не связаны;
- **−1** — противоположные стили: сильные стороны одного — это слабые стороны другого.

Маленький пример всего с тремя навыками (отбор, пас, удар):

- Игрок A: 80, 70, 60. Среднее 70, значит его профиль +10, 0, −10.
- Игрок B: 70, 60, 50. Среднее 60, значит его профиль тоже +10, 0, −10. B слабее, но косинус с A равен **1**: стиль тот же.
- Игрок C: 60, 70, 80. Среднее 70, значит его профиль −10, 0, +10. Косинус с A равен **−1**: это бомбардир, а не отбирающий.

Поскольку мы сначала вычли собственное среднее каждого игрока, длина стрелки (его уровень) не учитывается, только
направление. Это и есть идея «форма, а не высота». У Пабло Росарио из «Ниццы» средний навык ниже, чем у Биссумы (70,2),
но его косинусное сходство с Биссумой — **0,79**, самое высокое в нашем итоговом списке.

Вратарей сравниваем по их собственным навыкам (прыжок, игра руками, реакция и так далее), потому что полевые навыки для
вратаря мало что значат.

### G. Почему не кластеризация?

Первая очевидная идея — **кластеризация**: пусть алгоритм K-Means разложит полузащитников по группам вроде
«отбирающие» и «плеймейкеры», а замену ищем внутри группы проданного игрока. Мы это попробовали (ноутбук 02). Группы
действительно имеют футбольный смысл, но **коэффициент силуэта** оказался всего 0,22. Силуэт сравнивает, насколько
игрок близок к своей группе и насколько к ближайшей чужой; значение около 0 означает, что группы накладываются друг на
друга. Оказалось, что стили — это **непрерывная шкала**, а не отдельные коробки. Два игрока на противоположных краях одной
группы могут играть совсем по-разному, поэтому метка группы слишком грубая для выбора замены. А непрерывная мера вроде
косинусного сходства может упорядочить всех кандидатов.

### H. Можно ли доверять мере сходства? Тест «узнай себя»

Стиль игрока мало меняется от сезона к сезону. Поэтому мы взяли профили 500 полузащитников из FIFA 22 и для каждого
искали самого похожего игрока среди **всех 6 064 полузащитников FIFA 21**. Если мера работает, лучшим совпадением должен
оказаться тот же игрок годом раньше. Так и было **в 86% случаев** (а в топ-10 он был в 92% случаев). Обычное расстояние
по сырым навыкам справилось хуже (84%), хотя ему еще и «помогает» уровень игрока, который за год почти не меняется.

### I. Фильтр стиля (`keep_good_fit`)

Теперь у каждого кандидата есть оценка стиля. Мы оставляем **лучшую половину**: всех, у кого оценка не ниже медианы по
набору кандидатов. В нашем примере медиана 0,58, поэтому из 535 кандидатов остается 268.

Почему фильтр, а не вес в итоговой оценке? Мы попробовали оба варианта, и решил бэктест (часть 6): когда стиль
подмешивался в оценку, выбор становился хуже, потому что система жертвовала слишком большим качеством ради сходства. А
как фильтр стиль отсекает игроков, которые делали бы другую работу, и качество выбора почти не страдает.

Для редких типов игроков медиана недостаточно строгая. У классического плеймейкера вроде Эриксена половина кандидатов
почти не имеет с ним ничего общего (медианная оценка стиля в его наборе около 0,10). Поэтому пользователь может задать
еще и **минимальное совпадение по стилю** (`min_fit`), например 0,6.

## Часть 4 · Вторая составляющая: будущее (обучение с учителем)

### J. Что мы хотим предсказать

Стиль говорит, кто *подходит*. Но он не говорит, кто будет *хорош*. Например, самые похожие на Каземиро игроки были в
основном старше 30 лет, то есть скоро стали бы хуже. Клуб покупает игрока на следующие сезоны, а не на прошлый.

Поэтому вторая составляющая отвечает на вопрос: **каким будет общий рейтинг этого игрока через два сезона?**

### K. Учимся на прошлом: обучающие примеры (`growth_pairs`)

Это **обучение с учителем**: мы показываем компьютеру много примеров, где ответ уже известен, и он учится находить
закономерность. Каждый пример — это один игрок в одном сезоне вместе с его рейтингом через два сезона. Например:
«Мбаппе в FIFA 17: 17 лет, рейтинг 79, «Монако», … → рейтинг 88 в FIFA 19».

Функция `growth_pairs` строит такие примеры: соединяет каждого игрока в каждом сезоне с этим же игроком через два
сезона. У игроков, которые исчезли из игры, «через два сезона» нет, поэтому для обучения их использовать нельзя. Значит,
модель учится отвечать «насколько он будет хорош, *если продолжит играть*». Игроков, которые исчезают, учитывает бэктест
(часть 6).

Для каждого примера модель видит **45 признаков**: общий рейтинг, потенциал, возраст, международную репутацию, уровень
и силу лиги, оставшиеся годы контракта, слабую ногу, финты, рост, роль и подробные навыки (включая пять вратарских —
они важны для вратарей).

### L. Золотое правило: никогда не использовать будущее (утечка данных)

Допустим, мы принимаем решение летом 2022 года. В этот момент мы знаем рейтинги FIFA 22, но не FIFA 23. Если бы модель
обучалась на примере вроде «FIFA 21 → FIFA 23», она использовала бы информацию из будущего, которой у реального клуба не
было бы. Это называется **утечкой данных** (data leakage): с ней модель выглядит блестяще на проверке и бесполезна в
реальной жизни.

Поэтому `train_growth_model` берет только те примеры, у которых «через два сезона» уже известно на дату решения:
начальный сезон плюс 2 должен быть не позже сезона решения. Для решения летом 2022 года (FIFA 22) это начальные сезоны
с FIFA 15 по FIFA 20, результаты которых — с FIFA 17 по FIFA 22. Получается **80 730 обучающих примеров**.

Для этого правила есть даже автоматический тест (`test_no_data_leakage` в папке `tests/`): он обучает модель один раз на
всех данных и второй раз — после удаления всех сезонов позже даты решения, и проверяет, что все прогнозы совпадают.

### M. Модель: градиентный бустинг (`HistGradientBoostingRegressor`)

Это главная обученная модель проекта, из библиотеки scikit-learn. **Тип задачи — регрессия**: модель предсказывает
число (рейтинг через два года), а не категорию.

Как она учится, простыми словами:

1. Начинает с очень грубого прогноза — одного числа для всех (примерно средний будущий рейтинг).
2. Для каждого игрока считает, насколько этот прогноз ошибся (настоящий ответ минус прогноз). Эта ошибка называется
   **остатком**.
3. Строит маленькое **дерево решений** — цепочку вопросов «да/нет», например «Он младше 21 года? Его потенциал больше
   общего рейтинга на 10 пунктов?». Дерево предсказывает не сам рейтинг, а **насколько ошибается текущий прогноз** для
   каждого типа игроков.
4. Добавляет к прогнозу небольшую часть исправления этого дерева. Эта часть называется **скоростью обучения** (learning
   rate), у нас она 5%.
5. Строит следующее маленькое дерево, которое исправляет ошибки, *оставшиеся* после предыдущих. Потом еще одно, и еще.

Наша модель строит 400 таких деревьев. Маленькая скорость обучения заставляет ее улучшаться медленно и осторожно, а не
переобучаться на нескольких необычных игроках. Вместе деревья находят закономерности, которые не поймает ни одно простое
правило: например, что потенциал очень важен в 19 лет и почти ничего не значит в 29.

Что означает название. **«Бустинг»** (усиление) — много слабых деревьев вместе дают одну сильную модель. **«Градиентный»**
— каждое новое дерево сдвигает прогнозы в ту сторону, где ошибка уменьшается быстрее всего. **«Hist»** — перед обучением
числа раскладываются по интервалам (гистограммам), поэтому модель обучается за несколько секунд.

Почему не нейросеть? Наши данные — это таблица на десятки тысяч строк. Для таких данных градиентный бустинг —
стандартный инструмент: он точный, быстро обучается, сам справляется с пропущенными значениями, и можно проверить, на
что он опирается. В самом задании сказано, что сложность модели — не самоцель.

### N. Насколько хорошо она работает?

Мы проверяли ее на сезонах, которых она никогда не видела (ноутбук 03 и `examples/check_predictions.py`). Соревнуются
три метода:

- **«Ничего не изменится»**: рейтинг через два года равен сегодняшнему. Рейтинги меняются медленно, так что это сильный
  базовый подход.
- **Линейная регрессия** по общему рейтингу, потенциалу и возрасту.
- **Наш градиентный бустинг.**

Для решений 2019 и 2020 годов средняя ошибка (MAE — средняя абсолютная ошибка) была 2,59 пункта рейтинга у «ничего не
изменится», 2,57 у линейной регрессии и **2,28** у нашей модели. Для решений 2021 года — 2,33 против **2,03**.

Для скаутинга еще важнее, правильно ли модель расставляет игроков по **порядку** роста. Для игроков 23 лет и младше
ранговая корреляция (Спирмена) между прогнозом и реальным ростом была **0,42**, а у собственного рейтинга потенциала EA
— **0,35**.

У модели есть две честные слабости. В некоторые проверочные годы она была слишком оптимистичной для всех примерно на
0,5–1 пункт — вероятно, потому что EA со временем меняла свой стиль выставления рейтингов. На *порядок* кандидатов это не
влияет. И она **слишком осторожна со звездами**: летом 2021 года она ожидала, что Педри и Беллингем дойдут примерно до 79,
а оба дошли до 85. Модель учится на том, что делают обычные игроки, поэтому исключительное развитие предсказать труднее
всего.

Для самого Биссумы модель предсказывает 81,1 через два года: ему 24, он уже на своем уровне, большого изменения не будет.

## Часть 5 · От оценок к решению

### O. Сортировка кандидатов (`score`)

Теперь у каждого из 268 оставшихся кандидатов есть прогноз рейтинга через два года. По умолчанию мы просто **сортируем
по этому прогнозу**.

Код устроен чуть шире. Он переводит каждый сигнал в **процентиль** внутри набора кандидатов (0 — худший в наборе,
1 — лучший), чтобы можно было складывать числа в совсем разных единицах. Сигналов три: совпадение по стилю, прогноз
рейтинга и цена (чем дешевле, тем выше). Итоговая оценка — взвешенное среднее этих процентилей. Веса по умолчанию:
0 у стиля (он уже используется как фильтр), 1 у прогноза и 0 у цены. Это то же самое, что сортировать по прогнозу.

Ползунок **«предпочитать дешевле»** в приложении переносит вес с прогноза на цену. При значении 0,3 оценка на 70%
состоит из будущего рейтинга и на 30% из дешевизны. В бэктесте это экономило около 28% на игроке, но снижало долю
успехов примерно с 56% до 41%. Клуб может выбрать этот компромисс, но он не бесплатный.

### P. Объяснения и флажки рисков (`explain`, `risk_flags`)

Список имен без причин бесполезен для спортивного директора. Для каждого рекомендованного игрока Finder пишет
объяснение в одну строку, например: *«79% совпадение по стилю · рейтинг 78 сейчас, прогноз 78 через 2 года · стоит 52%
от стоимости Биссумы»*.

Еще он добавляет простые **флажки рисков**, каждый связан с известной слабостью футбольных данных:

- **игрок скамейки** (bench player): клуб записывает его как запасного или резервиста. Данных о сыгранных минутах у нас нет, поэтому это наша замена признаку «возможно, мало игрового времени, чтобы доверять его рейтингу».
- **более слабая лига** (weaker league): сила его лиги больше чем на 3 пункта ниже лиги продающего клуба. Рейтинги разных лиг не до конца сравнимы.
- **контракт заканчивается** (contract ending): остался максимум год. Хорошо для цены, но им заинтересуются и другие клубы.
- **мало места для роста** (little growth left): 27 лет и старше.

## Часть 6 · Откуда мы знаем, что это работает: бэктест (`src/backtest.py`)

Короткий список всегда выглядит убедительно: любой метод выдаст какие-нибудь имена. Настоящий вопрос другой: **были бы
эти игроки на самом деле удачными покупками?** Чтобы ответить, мы переигрываем историю.

### R. Переигрываем 750 решений

Мы встаем в конец трех прошлых сезонов: FIFA 19, FIFA 20 и FIFA 21 (лето 2019, 2020 и 2021 годов). В каждом выбираем
**250 случайных «проданных» игроков**: состоявшихся игроков высших дивизионов с рейтингом от 70 до 84 и возрастом от 22
до 30 лет. Для каждого делаем вид, что клуб его продает, и у клуба есть **60% его стоимости** на покупку, его зарплата как
потолок, ограничение по возрасту 28 лет и минимальный уровень на 12 пунктов ниже его.

Для каждого случая модель роста переобучается только на том, что было известно в тот момент (правило против утечки из
раздела L). Затем **восемь методов** выбирают по пять замен из **одного и того же набора кандидатов**, поэтому любая
разница объясняется только методом и ничем больше:

- наш Finder (фильтр стиля + модель роста);
- Finder с минимальным совпадением по стилю 0,6;
- Finder, который предпочитает более дешевых игроков;
- модель роста без фильтра стиля;
- наш первый вариант (стиль подмешан в оценку);
- «самый высокий рейтинг, который я могу себе позволить» — так поступил бы обычный скаут;
- «самый высокий потенциал, который я могу себе позволить» — классическое правило «покупай молодых»;
- и случайный выбор, как нижняя планка.

### S. Что считается успехом

Через два сезона выбранный игрок считается **успехом**, если он все еще в игре **и** его рейтинг не более чем на 3
пункта ниже проданного игрока. Другими словами, он стал настоящей заменой.

Игроки, которые исчезли из игры, считаются **неудачей**. Это важно: примерно 38% игроков уходят из игры в течение двух
лет. Если оценивать только тех, кто остался, любой метод будет выглядеть лучше, чем на самом деле. Эта ошибка называется
**ошибкой выжившего** (survivorship bias).

### T. Результат

По 750 решениям игроки, выбранные Finder, были успешны в **56%** случаев. «Самый высокий рейтинг, который могу себе
позволить» — 43%, «самый высокий потенциал» — 44%, случайный выбор — 11%. Кроме того, игроки Finder реже выпадали из игры
(13% против 20%), гораздо больше походили по стилю на проданного игрока (0,74 против 0,60) и стоили столько же (около
3,8 млн евро против 3,9 млн). Finder выигрывает не за счет того, что тратит больше.

### U. Это не случайность? Бутстрэп

Даже на 750 случаях разница может быть отчасти случайной. **Бутстрэп** это проверяет. Мы случайно вытаскиваем 750
случаев из наших 750 *с возвращением* (какие-то случаи попадаются дважды, какие-то ни разу) и заново считаем преимущество
Finder. Повторяем это 2000 раз. Средние 95% полученных значений — это **95-процентный доверительный интервал**. Для Finder
против «самого высокого рейтинга» он **от +11 до +15 пунктов**: целиком выше нуля, значит преимущество не случайное. Мы
пересобираем целые случаи, а не отдельных игроков, потому что пять игроков одного случая связаны одним проданным игроком
и одним набором кандидатов, то есть не независимы.

### V. Пытаемся сломать результат

Мы также специально меняли условия. Finder — лучший метод в каждом сезоне отдельно (2019, 2020 и 2021), при более строгом
определении успеха («так же хорош, как проданный») и при более мягком (до 5 пунктов ниже), а также при **бюджете на 20%
меньше** (43% против 30%).

И мы показываем, где он слабее всего. В 2021 году его отрыв всего около 2 пунктов, потому что результаты измерялись в
январе 2023 года, в середине сезона, и у молодых игроков было меньше времени вырасти. А при самом строгом определении
он идет вровень с «самым высоким потенциалом».

### W. Чему нас научил бэктест

Бэктест не просто подтвердил финальную схему — он ее **создал**. Наш первый вариант смешивал 40% стиля, 40% будущего и
20% цены в одну оценку. Он был успешен только в 36% случаев — хуже, чем обычный скаут. Именно поэтому стиль стал
фильтром, а не весом.

## Часть 7 · Идея, от которой мы отказались, и почему это важно

### X. Модель стоимости: цена в EA — это формула

Классическая идея «Moneyball» — найти игроков, которые **дешевы для своего уровня**. Мы построили модель градиентного
бустинга, которая предсказывает рыночную стоимость игрока по его рейтингу, потенциалу, возрасту, репутации, контракту и
роли. План был такой: называть игрока «недооцененным», если его реальная цена сильно ниже предсказанной.

Модель предсказала цену EA **с точностью примерно до 2%**. Это значит, что рыночная стоимость в EA — почти **формула** из
рейтинга, потенциала, возраста и роли. Скрытых выгодных покупок в ценах EA нет, и «недооцененные» игроки потом не стали
лучше остальных.

Мы проверили и известную идею «дешевых лиг»: при том же рейтинге игроки японской лиги стоят вдвое дешевле, чем в Ла Лиге.
Но они также старше и с меньшим потенциалом. Если это учесть, лига меняет цену всего примерно на 0,2%. Это была **скрытая
третья переменная** (confounding): скрытый фактор (возраст и потенциал) создал закономерность, которая выглядела как
причина и следствие.

Этот отрицательный результат изменил всю стратегию. Если цена — формула от сегодняшнего рейтинга, потенциала и возраста,
то обыграть ее можно только одним способом: **знать будущее лучше, чем формула**. Ровно это делает модель роста, и
поэтому она стала ядром системы.

Это же главное ограничение проекта: цены EA — не реальные трансферные суммы. Чуамени стоил в FIFA 52 млн евро, а
«Реал», по сообщениям, заплатил около 80 млн или больше. Короткий список — отправная точка для живых скаутов, а не
окончательный ответ.

## Часть 8 · Проверяем, что код соблюдает правила

### Y. Автоматические тесты (`tests/test_finder.py`)

Команда `pytest -v tests/` запускает 16 проверок примерно за 15 секунд. Они проверяют, что:

- ни один рекомендованный игрок не нарушает бюджет, потолок зарплаты, ограничение по возрасту или минимальный уровень;
- игроки собственного клуба никогда не рекомендуются;
- каждый кандидат играет совместимую роль;

- удаление всех будущих сезонов не меняет ни одного прогноза (тест на утечку данных);
- два запуска дают в точности одинаковый список.

## Часть 9 · Цели клуба и план трансферов

До сих пор клуб продавал одного игрока и хотел замену того же стиля. Но настоящие клубы часто продают нескольких игроков
за одно окно, с одним бюджетом, и хотят не всегда одного и того же. Теперь проект умеет и то и другое (ноутбук 06).

### Три цели

- **Замена того же стиля** (`replace`, по умолчанию): всё, что описано выше. Фильтр стиля, затем сортировка по прогнозу
  рейтинга.
- **Усиление состава** (`squad`): без фильтра стиля, просто кандидат с лучшим прогнозом рейтинга через два года. Полезно,
  если проданный игрок и так не подходил команде.
- **Заработок** (`profit`): сортировка по **ожидаемой прибыли**. Для этого нужны две новые модели, обученные по тому же
  правилу без утечки данных, что и модель роста:
  - модель **регрессии**, которая предсказывает **рыночную стоимость игрока через два года** (типичная ошибка 39% против
    50% у «стоимость не изменится»);
  - модель **классификации**, которая предсказывает **вероятность, что он останется в игре** через два года (AUC 0,78).
    Игрока, который исчез, нельзя перепродать, поэтому его перепродажа считается за €0. Модель хорошо откалибрована: если
    она говорит 30%, остаются около 30%; если 95% — около 95%. Ниже 50% Finder показывает флажок «высокий риск выбывания».

  Ожидаемая прибыль = вероятность остаться × прогноз стоимости через два года − цена. В бэктесте на 750 случаях режим
  «заработок» принёс около **€5,5M на игрока** через два года. Это ничья с простым правилом «покупай самый высокий
  потенциал» (€5,3M): по деньгам он не лучше, но его игроки лучше как замена (49% против 44%) и реже исчезают.

### Несколько игроков, один бюджет: план трансферов

Представьте «Брайтон» летом 2022 года: он продал и Биссуму, и Кукурелью, и у него €45M на обе замены. Простой способ —
разделить деньги вручную (доля на каждую позицию) и выбирать каждую замену отдельно. Но так деньги не могут переходить
между позициями.

**План трансферов** (`ReplacementFinder.plan`) решает всю задачу сразу с помощью **целочисленного программирования**
(функция `milp` из scipy). Для каждой пары (проданный игрок, кандидат) есть переменная: 1 — покупаем, 0 — нет. Правила
записаны как ограничения: ровно одна покупка на каждого проданного игрока; никого не покупаем дважды; сумма цен не больше
бюджета. Решатель находит комбинацию с наибольшим общим выигрышем (для замены того же стиля: прогноз рейтинга минус
рейтинг проданного игрока).

Для каждого проданного игрока оптимизатор рассматривает лучших кандидатов и всех «лучших за свою цену» (никто дешевле не
даёт больший выигрыш). Это гарантирует, что план никогда не хуже (по прогнозу), чем деление бюджета вручную. В бэктесте
(по 450 клубов) совместный план давал настоящую замену в **65% против 61%** случаев при двух проданных игроках и в
**67% против 60%** при трёх. Обе разницы статистически значимы, и преимущество растёт с числом игроков. Наш первый
оптимизатор проиграл простому методу; бэктест это показал, и так мы нашли и исправили ошибку.

### Фокус: говорим плану, что важно

Клуб может сказать: «этим летом усиливаем полузащиту» (или атаку, или защиту). В плане выигрыш позиций в фокусе считается
вдвое, поэтому оптимизатор готов тратить туда больше. «Брайтон» с €45M: без фокуса покупает Максимовича (€20,5M) и Давида
Раума (€23,5M); с фокусом на полузащиту — Беннасера (€33,5M) и дешёвого 18-летнего крайнего защитника; с фокусом на
защиту — Ренана Лоди (€36,5M) и более дешёвого полузащитника. Фокус — это желание клуба, а не прогноз, поэтому сверять его с
реальностью не нужно; проверяем только, что деньги действительно смещаются (это делает автотест).

## Z. Вся система на одном дыхании

Рейтинги FIFA (10 миллионов еженедельных строк) очищаются до одной строки на игрока за сезон, на конец сезона. Когда клуб
продает игрока, бизнес-правила оставляют тех, кто может играть его роль и проходит ограничения по деньгам и возрасту.
**Обучение без учителя** (косинусное сходство формы профиля навыков) оставляет половину, которая играет больше всего
похоже на него. **Обучение с учителем** (градиентный бустинг, обученный только на прошлом) предсказывает рейтинг каждого
через два года, и мы сортируем по этому прогнозу, с объяснениями и флажками рисков. **Бэктест на 750 исторических
решениях** — без данных из будущего, с одинаковым набором кандидатов для всех методов, с выбывшими игроками как неудачами
и с проверкой бутстрэпом — показывает, что это примерно на 13 процентных пунктов лучше правила «купи лучший рейтинг,
который можешь себе позволить». По дороге данные опровергли четыре из шести наших идей, и каждое опровержение сделало
систему лучше.

### Словарик

| Термин | Что значит в этом проекте |
|---|---|
| Обучение с учителем | Учимся на примерах с известным ответом (игрок сейчас → его рейтинг через два года) |
| Обучение без учителя | Ищем структуру без ответов (кто играет похоже) |
| Регрессия | Задача, где нужно предсказать число, а не категорию |
| Признак (feature) | Один входной столбец для модели: возраст, потенциал, навык и т.д. |
| Целевая переменная (target) | То, что предсказываем: рейтинг через два сезона |
| Профиль стиля | Каждый навык минус средний навык самого игрока: форма, а не высота |
| Косинусное сходство | Насколько профили двух игроков смотрят в одну сторону (от −1 до 1) |
| K-Means / силуэт | Метод кластеризации / оценка того, насколько четко разделены кластеры |
| Дерево решений | Цепочка вопросов «да/нет», которая приводит к ответу |
| Градиентный бустинг | Много маленьких деревьев, каждое исправляет ошибки предыдущих |
| Остаток (residual) | Ошибка прогноза: настоящий ответ минус прогноз |
| Скорость обучения | Какую часть исправления каждого дерева мы берем (у нас 5%) |
| Утечка данных | Модель случайно учится на информации из будущего |
| Базовый подход (baseline) | Простой метод, который модель должна обыграть |
| MAE | Средняя абсолютная ошибка: средний размер промаха прогноза |
| Корреляция Спирмена | Насколько предсказанный порядок совпадает с реальным (1 — идеально) |
| Бэктест | Переигрываем прошлые решения только на прошлых данных и смотрим результат |
| Ошибка выжившего | Смотрим только на оставшихся игроков, и результат кажется лучше, чем есть |
| Бутстрэп | Многократно пересобираем выборку, чтобы понять, не случайный ли результат |
| Скрытая третья переменная (confounding) | Скрытый фактор создает обманчивую связь (возраст за «дешевыми лигами») |
